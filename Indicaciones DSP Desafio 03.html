I. Indicaciones generales

  1. Lean completo el documento antes de empezar y distribuyan el trabajo con tiempo dentro de los 15 días. Los puntos se asignan por requerimiento funcionando, no por intentos parciales.
  2. El trabajo se realiza en parejas. Ambos integrantes son responsables de todo el contenido y deben poder explicar cualquier parte durante la defensa. Cualquier copia entre parejas o ayuda de terceros anula la evaluación de los involucrados.
  3. Material permitido: sus guías de laboratorio 9, 10, 11 y 12, sus proyectos previos y la documentación oficial de Microsoft.
  4. Material no permitido: asistentes de inteligencia artificial, chats, mensajería y cualquier ayuda de otra persona.
  5. Todos los proyectos usan la misma versión de .NET. Para AutoMapper usen las versiones indicadas en la Guía 11.
  6. Deben poder ejecutar y demostrar su solución en el equipo del aula cuando el docente lo solicite.
  7. Hagan commits por fase durante el parcial, con aportes de ambos integrantes. Un único commit al final se penaliza.
  8. Las dudas sobre el enunciado se consultan al docente. Las dudas de implementación no se resuelven.

II. Objetivo

Que los estudiantes demuestren que son capaces de:

  • Diseñar un modelo relacional y construirlo con EF Core mediante migraciones (código primero).
  • Exponer el modelo en una Web API RESTful con DTOs, AutoMapper, Swagger y autenticación JWT con roles.
  • Consumir la API desde un cliente ASP.NET Core MVC, manejando el token, los roles y los errores HTTP.
  • Generar un módulo de reportes de solo lectura a partir de una base de datos existente (base de datos primero).
  • Prevenir la pérdida de cambios en ediciones simultáneas (concurrencia optimista).

III. Escenario

El laboratorio de computación de la facultad presta equipos (laptops, proyectores, kits de IoT, tarjetas Arduino) a docentes y estudiantes. Hoy el control se lleva en una hoja de cálculo y se pierden equipos o no se sabe quién los tiene.

Ustedes deben construir un sistema de tres componentes que comparten una sola base de datos SQL Server:

Componente Proyecto Tecnología
Servicio EquiposAPI ASP.NET Core Web API, EF Core código primero, JWT
Cliente de operación EquiposMVC ASP.NET Core MVC, HttpClient, Session
Módulo de reportes EquiposReportes ASP.NET Core MVC, EF Core base de datos primero

Restricción de arquitectura

EquiposMVC y EquiposReportes nunca escriben directo en la base de datos. Toda escritura pasa por la API. EquiposReportes solo lee, y lo hace con un usuario de SQL Server que tiene únicamente permiso de lectura.

IV. Modelo de datos

Entidades mínimas (pueden agregar campos, no quitar):

Entidad Campos Restricciones
Categoria Id, Nombre Nombre único, máximo 100 caracteres
Equipo Id, CodigoInventario, Nombre, Descripcion, CategoriaId, Estado, RowVersion CodigoInventario único. Estado: Disponible, Prestado, Mantenimiento. RowVersion para concurrencia
Usuario Id, Username, PasswordHash, Email, Rol Username único. Rol: Admin, Docente, Estudiante
Prestamo Id, EquipoId, UsuarioId, FechaPrestamo, FechaVencimiento, FechaDevolucion, Observaciones FechaDevolucion nula mientras el equipo no se devuelva

Relaciones: Categoria 1-N Equipo, Equipo 1-N Prestamo, Usuario 1-N Prestamo. Todas con DeleteBehavior.Restrict.

V. Reglas de negocio

  1. Solo se puede prestar un equipo cuyo Estado sea Disponible. Si no lo está, la API responde 409 Conflict con un mensaje claro.
  2. Al registrar un préstamo, el Estado del equipo pasa a Prestado en la misma transacción (un solo SaveChanges).
  3. La FechaVencimiento no puede ser anterior a hoy ni mayor a 7 días desde la fecha del préstamo.
  4. Al registrar la devolución se llena FechaDevolucion y el equipo vuelve a Disponible.
  5. Un equipo con préstamos históricos no se puede eliminar. La API responde 409.
  6. Permisos por rol:
Acción Admin Docente Estudiante
CRUD de categorías y equipos Sí No No
Registrar usuarios Sí No No
Registrar préstamo y devolución Sí Sí No
Ver equipos disponibles Sí Sí Sí
Ver préstamos Todos Todos Solo los propios
Reportes Sí No No

VI. Requerimientos por componente

Parte 1: EquiposAPI

  • Modelo creado con EF Core código primero, con migraciones. Las llaves foráneas y los índices únicos deben existir en SQL Server.
  • Datos semilla para Categoria. Los usuarios no se siembran con HasData.
  • Los endpoints reciben y devuelven DTOs, nunca entidades. Debe haber DTOs distintos para crear, actualizar y listar.
  • AutoMapper y Swagger configurados.
  • La cadena de conexión y la clave JWT se guardan en User Secrets o variables de entorno. No se permiten contraseñas ni claves en appsettings.json, en Program.cs ni en el repositorio.

Endpoints mínimos:

Método Ruta Descripción Rol
POST /api/auth/login Devuelve token JWT Anónimo
POST /api/auth/register Registra usuario Admin
GET /api/categorias Lista categorías Autenticado
POST, PUT, DELETE /api/categorias Mantenimiento Admin
GET /api/equipos?texto=&categoriaId=&estado= Lista con filtros combinables Autenticado
GET /api/equipos/{id} Detalle con categoría Autenticado
POST, PUT, DELETE /api/equipos Mantenimiento Admin
POST /api/prestamos Registra préstamo Admin, Docente
PUT /api/prestamos/{id}/devolucion Registra devolución Admin, Docente
GET /api/prestamos?soloVencidos=true Lista según el rol del token Autenticado

Parte 2: Seguridad

  • Las contraseñas se almacenan como hash (PasswordHasher<Usuario> o BCrypt.Net-Next), nunca en texto plano.
  • Si la tabla Usuarios está vacía al iniciar, un seeder crea un Admin inicial. La contraseña inicial viene de configuración, no del código.
  • El token incluye el identificador y el rol del usuario como claims, tiene fecha de expiración y su clave tiene al menos 32 caracteres.
  • Los endpoints se protegen con [Authorize] y [Authorize(Roles = ...)] según la tabla de la sección V.
  • En el listado de préstamos, el Id del usuario se toma del token. El Id nunca se recibe por parámetro.
  • El registro de un Username repetido devuelve 409.

Parte 3: Concurrencia optimista

  • Equipo usa RowVersion como token de concurrencia.
  • El DTO de actualización transporta RowVersion y la API lo respeta al guardar.
  • Si dos usuarios editan el mismo equipo, el segundo recibe 409 con un mensaje claro.

Parte 4: EquiposMVC

  • Aplicación MVC sin autenticación propia que consume la API. El token se envía automáticamente en cada solicitud, sin modificar DefaultRequestHeaders de un cliente compartido.
  • La URL base de la API se lee de configuración, no se escribe en controladores ni servicios.
  • Un servicio y un controlador por recurso (equipos, categorías, préstamos, autenticación), con vistas Index, Create, Edit y Delete.
  • Al iniciar sesión se guardan en Session el token, el rol y el nombre de usuario. Use una sola convención de nombres (Username o Email) en la vista, el modelo y la API.
  • El menú depende del rol: el Estudiante solo ve Equipos disponibles y Mis préstamos. El Admin ve todo.
  • Manejo obligatorio de errores HTTP:
Código Comportamiento del cliente
401 Limpiar la sesión y redirigir al login con mensaje de sesión expirada
403 Mostrar vista de acceso denegado
409 Mostrar el mensaje de la API dentro del formulario, sin perder lo que el usuario escribió
5xx Mostrar mensaje genérico, sin exponer detalles internos
  • La vista Index de Equipos incluye filtros (texto, categoría, estado) y paginación de 10 registros por página.
  • La vista Edit de Equipo envía RowVersion de vuelta a la API.

Parte 5: EquiposReportes

  • Se crea un inicio de sesión y un usuario reportes en SQL Server con rol db_datareader únicamente.
  • El contexto y las clases se generan desde la base existente (Scaffold-DbContext). La cadena de conexión no queda escrita en OnConfiguring: se mueve a User Secrets y el contexto se registra con inyección de dependencias.
  • Todas las consultas usan AsNoTracking() y proyectan a ViewModels. No se devuelven entidades a la vista.
  • El acceso exige iniciar sesión contra /api/auth/login y solo permite el rol Admin.
  • Reportes con LINQ, cada uno con filtros (rango de fechas, categoría):
Reporte Descripción
Inventario por categoría Cantidad de equipos por categoría y por estado
Préstamos vencidos FechaVencimiento menor a hoy y FechaDevolucion nula, con nombre de usuario y días de atraso
Top 5 equipos más prestados Con conteo de préstamos en un rango de fechas
Historial por usuario Búsqueda por Username con todos sus préstamos

VII. Casos que serán verificados

El docente revisará en la defensa, y ustedes deben documentar con la colección de Postman o capturas, como mínimo:

Nº Caso
1 Login correcto devuelve token con rol
2 Login con contraseña incorrecta devuelve 401
3 Endpoint protegido sin token devuelve 401
4 Estudiante intenta crear un equipo y recibe 403
5 Registrar usuario con Username repetido devuelve 409
6 Prestar un equipo que ya está Prestado devuelve 409
7 FechaVencimiento a 15 días es rechazada
8 Eliminar equipo con historial devuelve 409
9 Dos ediciones simultáneas del mismo equipo, la segunda devuelve 409
10 Un Estudiante solo ve sus propios préstamos aunque cambie parámetros en la URL
11 Token expirado en el cliente MVC redirige al login
12 Los cuatro reportes muestran datos coherentes con SSMS

VIII. Entregables

Se entrega, en el medio indicado por el docente (repositorio Git o carpeta comprimida), dentro del plazo de 15 días del parcial:

  1. Las tres soluciones: EquiposAPI, EquiposMVC y EquiposReportes.
  2. El script SQL generado a partir de las migraciones.
  3. La colección de Postman exportada.
  4. Un archivo README con las instrucciones para ejecutar el sistema (versión de .NET, secretos requeridos, orden de arranque).

IX. Criterios de evaluación

Cada criterio se califica en uno de cuatro niveles. El docente asigna la nota dentro del rango del nivel que mejor describe el trabajo.

Criterio Deficiente Regular Bueno Sobresaliente
Modelo, migraciones y relaciones correctas
10 puntos		 0–4. Faltan entidades o relaciones, o la base no se crea desde migraciones. 5–6. Entidades y migraciones presentes, pero faltan restricciones (índices únicos, longitudes, Restrict) o hay relaciones mal definidas. 7–8. Modelo completo con migraciones y relaciones correctas. Falta un detalle menor, como la semilla de Categoria o un índice. 9–10. Modelo completo y verificado en SSMS: llaves foráneas, índices únicos, Restrict, Estado como texto y semilla de Categoria.
API REST con DTOs, AutoMapper, Swagger y reglas de negocio
15 puntos		 0–6. Menos de la mitad de los endpoints funciona, o devuelve entidades en lugar de DTOs. 7–9. Endpoints básicos funcionan, pero los DTOs no están separados, faltan filtros o varias reglas de negocio no están implementadas. 10–12. Endpoints completos con DTOs y AutoMapper. Las reglas de negocio tienen fallas menores (códigos 409 o validación de fechas incompletos). 13–15. Todos los endpoints y filtros funcionan con DTOs distintos, AutoMapper y Swagger. Las cinco reglas se cumplen con código y mensaje claros, y el préstamo es transaccional.
Seguridad: hash, roles, claims, autorización por endpoint, secretos fuera del código
20 puntos		 0–8. Contraseñas en texto plano, o endpoints sin proteger. 9–12. Hay hash y JWT, pero la autorización por rol es incompleta, el Id de usuario se recibe por parámetro o hay secretos en archivos versionados. 13–16. Hash, claims y roles correctos en casi todos los endpoints, con secretos fuera del código. Falla un detalle (seeder del Admin, Username repetido o longitud y expiración de la clave). 17–20. Hash, claims con Id y rol, autorización por endpoint según la tabla, el Estudiante solo ve lo propio desde el token, seeder con contraseña de configuración, Username repetido devuelve 409 y secretos en User Secrets.
Concurrencia optimista funcionando de extremo a extremo
10 puntos		 0–4. No hay RowVersion o no se usa. 5–6. RowVersion está en el modelo pero no viaja en el DTO ni se compara al guardar, y la segunda edición sobrescribe. 7–8. La API detecta el conflicto y devuelve 409, pero el cliente MVC no envía RowVersion o no muestra el mensaje. 9–10. Funciona de extremo a extremo: RowVersion en el DTO, 409 en la API y mensaje en MVC sin perder lo escrito. Probado con dos ediciones simultáneas.
Cliente MVC: CRUD, menú por rol, manejo de 401, 403 y 409, filtros
15 puntos		 0–6. CRUD incompleto, o el cliente accede directo a la base de datos. 7–9. El CRUD funciona, pero el token no se envía automáticamente, el menú no depende del rol o no se manejan los errores HTTP. 10–12. CRUD y menú por rol correctos, con 401 y 403 manejados. Falla el 409 o el 5xx, o faltan filtros o paginación. 13–15. CRUD de todos los recursos, token enviado por handler, menú por rol, 401, 403, 409 y 5xx tratados como se pide, filtros combinados y paginación de 10.
Reportes con base de datos primero, solo lectura y filtros

Cuatro reportes correctos con filtros de fecha y categoría, ViewModels, usuario db_datareader, cadena en User Secrets y datos que coinciden con SSMS.
Pruebas documentadas y calidad del repositorio (commits por fase, README)

Los 12 casos con resultado esperado, obtenido y evidencia, más colección de Postman, script SQL, README completo y commits por fase de ambos integrantes.
